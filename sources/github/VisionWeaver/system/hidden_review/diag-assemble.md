# Diagnosis — Fireside Ep1 v3 ASSEMBLE timeout (Oct 21 2026)

**Worker:** diagnostic, read-only (no code changed, no renders fired). Date: Oct 22 2026 (CDT).
**Scope:** `loop/stages.py` + `loop/run.py` assemble paths, the Crossroads assembler they invoke,
the Oct 21 `fireside-ep01-v3` manifests, and every artifact on disk.
**Bottom line up front:** this was **not a hang**. The assembler was killed mid–pass 1 by the
loop's 1,800 s timeout because the job, at the assembler's own settings, needs
**~47 min in the best measured case and ~1¾–2 hours under Oct 21's actual load**
on this VM — the 30-minute budget could not have held under any observed condition.
A finished, caption-burned master **does exist** on disk — but no loop manifest records it,
and filesystem evidence says it was finished outside a clean in-system assembler run.

### 1c. Why it cannot fit in 30 minutes — measured, not estimated

Benchmarks run Oct 22 on this VM (2 vCPU, 7.7 GB RAM, ffmpeg 8.1.2), using the assembler's
exact encode settings and the real Ep1 clips, outputs to `/tmp`:

| Pass | Replica | Result |
|---|---|---|
| Pass 1 (video only — no audio mix), run A | concat of the 5 real clips → `scale/crop/fps=30`, libx264 `-preset medium -crf 20`, 120 s of output | **536.0 s wall** (user 855 s) = **0.224× realtime, 6.7 fps** |
| Pass 1, run B (same command, background completion, less contended box) | identical | **147.8 s wall** (user 196.7 s) = **0.81× realtime** |
| Pass 2 (caption burn) | `subtitles=` burn on 60 s, libx264 `-preset medium -crf 20` | **85.7 s wall** (user 91.5 s ≈ **1 core only** — libass serialises the encode) = **0.70× realtime** |

Encode speed on this shared 2-vCPU VM is **highly load-sensitive** (run A ran while
sibling review workers were active; run B completed on a quieter box). Extrapolated
to the full 1,054.38 s picture, the honest range is:

- **Pass 1 ≈ 1,300–4,700 s (~22–79 min)** for video alone; the real pass 1 also runs
  the 19-input `amix`/`apad` graph + AAC encode. Observed on disk Oct 21: the pass-1
  output `ep01-v3.mp4.nocap.mp4` was being written from **20:14:50Z to 21:42:54Z
  (~88 min)** — slower than either benchmark, on an evening when animate/TTS work
  was running concurrently.
- **Pass 2 ≈ ~1,500 s (~25 min)**.
- **Total ≈ 2,800–6,800 s (~47 min – 1 h 55 m)** vs a **1,800 s** budget. Even the
  most favourable measurement (run B + pass 2) totals ~47 min — still **1.6× the
  entire timeout**. The timeout was unavoidable at these settings under any
  observed load; under Oct 21's actual load it was hopeless by ~4×.

End-to-end corroboration: first ffmpeg write 20:14:50Z → finished captioned master
mtime **22:14:17Z** = **1 h 59 m 27 s** of wall clock for the whole assembly episode.

**Root cause statement:** `assemble.py` performs **two sequential full-length libx264
`-preset medium -crf 20` re-encodes** of a 17.6-minute 720p programme on a 2-vCPU VM
(pass 1 at assemble.py:178, pass 2 at assemble.py:189), measuring 0.22–0.81× realtime
for pass 1 depending on box load. The loop's then-current 1,800 s cap (see §2) killed it
during pass 1, before the `.nocap.mp4` intermediate was even finished. No deadlock, no
missing file, no retry loop — ordinary, predictable, CPU-bound slowness that nobody
had measured against the timeout.

## 2. Code evidence (file:line)

**Loop side — `~/workspace/visionweaver/loop/stages.py`**

- `stages.py:43-44` — `sh()` helper: `subprocess.run(..., timeout=kw.pop("timeout", 300))`.
  Default cap for any stage subprocess is **300 s** unless overridden.
- `stages.py:199-213` — `crossroads` assemble mode: builds
  `python3 ASSEMBLER <edl> -o <out> [--shots-dir] [--audio-dir]` and calls it at
  **line 212 as `sh(cmd, timeout=7200, ...)` in the file as it stands today.**
  The 151437 manifest proves the value at runtime on Oct 21 was **1800**, not 7200.
  `stages.py` mtime is **2026-10-21 20:46:33Z** — two minutes *after* the failure
  manifest was written (~20:44:37Z) — i.e. the timeout was raised 1800 → 7200
  immediately after the failure, but 7200 is not a principled value either: it
  covers the measured total range (~2,800–6,800 s) only at the favourable end and
  leaves little headroom on a loaded box.
- `stages.py:199-213` — crossroads mode has **no idempotency check**: unlike `still`
  mode (`stages.py:179-180`, returns `reused` if the master exists), every crossroads
  invocation re-runs the full ~2 h encode even if a finished master is already on disk.
- `stages.py:175-197` — `still` mode: both ffmpeg calls go through `sh()` with **no
  timeout argument → 300 s cap**. Fine for short loop-test episodes; a latent trap for
  any long `still` job.
- `stages.py:165-174` — `prebuilt` mode: existence check only, no encode. Not implicated.
- `run.py` — no stage-level timeout of its own; writes the manifest only when `main()`
  returns, which is why a killed run still produced its manifest (the exception was
  caught and recorded) but a hard-killed loop would leave none.

**Assembler side — `~/workspace/goals/crossroads-of-identity-episode-1-production/files/assembler/assemble.py`**
(path confirmed via `stages.py:22`: `ASSEMBLER = .../goals/crossroads-of-identity-episode-1-production/files/assembler/assemble.py`)

- `assemble.py:46-47` — `run()`: `subprocess.run(cmd, capture_output=True, text=True)` —
  **no timeout at all**, and all ffmpeg output is buffered, so during a ~90-minute pass
  there is **zero progress visibility** from inside the assembler.
- `assemble.py:129-134` — pass 1 command: `-f concat -safe 0 -i <concat_list>` plus one
  `-i` per audio event (**20 inputs total**).
- `assemble.py:138-141` — video chain: `scale=1280:720:force_original_aspect_ratio=increase,
  crop=1280:720,fps=30,format=yuv420p`. Sources are already 1280×720 but at **24 fps**,
  so every frame is also fps-converted 24 → 30.
- `assemble.py:144-156` — per-event audio: `aresample=48000, volume, adelay=<ms>|<ms>,
  apad=whole_dur=1054.880` ×19, then `amix=inputs=19:normalize=0`.
- `assemble.py:161-173` — if the EDL names a captions file and it exists, the main output
  is diverted to `<output>.nocap.mp4` and captions are deferred to a second pass.
  (Comment at :161-162 records the Oct 21 fix: ffmpeg rejects `-vf subtitles=` alongside
  `-filter_complex`. True — but subtitles can legally be a node *inside* the
  `-filter_complex` graph; see fix §5.)
- `assemble.py:178` — pass 1 encode: `-c:v libx264 -preset medium -crf 20`.
- `assemble.py:184-192` — pass 1 `run(cmd)`, then pass 2:
  `ffmpeg -i <nocap> -vf subtitles='…' -c:v libx264 -preset medium -crf 20 -c:a copy …`,
  then `os.remove(main_out)` (:192) and `os.remove(concat_list)` (:193).
  **Neither removal ever happened for Ep1 v3** — both files still sit in the output
  folder today (see §3), which is positive proof the delivered master did **not**
  complete through this code path end-to-end.

**Candidate causes checked and ruled out**

| Candidate | Verdict |
|---|---|
| No timeout on subprocess | **Partially true, contributing defect** — true inside `assemble.py:47`; the loop *did* impose one (1800 s) externally. |
| Caption pass re-encodes full length | **True, contributing** — ~25 min of the ~110 min total (assemble.py:187-191). |
| Huge input resolution / bitrate | **No** — sources are 1280×720, 3.1–7.3 Mb/s, ~35 MB total. |
| Waiting on stdin | **No** — ffmpeg is launched with `-y` and captured pipes; nothing reads stdin. |
| EDL paths → missing/remote files | **No for the timeout run** — but it *was* the failure of three sibling runs the same day: 143034 & 151030 died on `FileNotFoundError: fireside-ep01-v3-edl.json` (EDL not yet built), 151400 on `missing clip ~/workspace/…/v3-ep01-gather.mp4` (unexpanded `~` in shots path). All fast fails, all fixed before 151437, whose run demonstrably resolved every path (concat list + timeline written, ffmpeg started). |
| Concat of mismatched codecs | **No** — all 5 clips are identical: H.264, 1280×720, 24 fps, 10.041667 s. |
| Infinite retry | **No** — no retry loop exists anywhere in the assemble path. |

**Orphan-process defect (consequence of the timeout):** when `sh()` hit 1,800 s,
`subprocess.run` killed `assemble.py` (its direct child) but **not ffmpeg, its
grandchild**. Proof: `.nocap.mp4` birth 20:14:50Z (13 s after the run started) but
mtime **21:42:54Z — 58 minutes after the loop run was already dead and manifested as
failed**. The concat list and timeline files were also *rewritten at 21:23:08Z/21:23:10Z*,
i.e. a further assembler launch touched the same outputs while the orphaned encode was
still writing — two writers, one output path, no locking. Any fix must kill the whole
process group on timeout (see §5).

## 6. Proposed minimal in-system fix (NOT applied — diagnosis only)

Ordered by leverage; items 1–2 are the actual cure, 3–4 are hygiene so it can't recur silently.

1. **`assemble.py` — burn captions inside pass 1; delete pass 2.**
   Append the subtitles filter as the last node of the existing `-filter_complex`
   graph (`[v]subtitles='<esc>'[vout]`, `-map [vout]`) instead of the separate
   `-vf` pass at :187-191, and drop the `.nocap.mp4` diversion at :173.
   The Oct 21 comment (:161-162) is correct that `-vf` can't coexist with
   `-filter_complex` — but a filter *inside* the graph is legal and standard.
   **Saves the entire second full-length encode (~25 min measured) and the 461 MB
   intermediate write.**
2. **`assemble.py:178` — `-preset medium` → `-preset veryfast`** (single remaining encode).
   Pass 1 at `medium` measures 0.22–0.81× realtime on this 2-vCPU VM depending on
   load; `veryfast` is typically 3–5× faster for this content class. Expected
   combined effect of 1+2: full assembly in roughly **10–20 min** (estimate —
   prove it with a 120 s proof encode before any full run, on a quiet box, and
   budget for the loaded-box case). Optional companion: set the EDL `output.fps`
   to **24** (the clips' native rate) to drop the 24→30 fps conversion.
3. **`stages.py` crossroads mode (:199-213) — add the reuse check `still` mode
   already has** (skip when the master exists and is newer than the EDL), and set the
   timeout from the measured post-fix duration with headroom (e.g. 3,600 s), not a guess.
4. **Timeout must kill the process group.** In `stages.py:sh()` and
   `assemble.py:run()`: launch with `start_new_session=True` and `os.killpg` on
   `TimeoutExpired`; give `assemble.py:run()` an explicit timeout and let ffmpeg's
   progress go to stderr instead of `capture_output` buffering, so a long assemble
   is observable while it runs. This kills the orphaned-ffmpeg failure mode proven in §2.

**Not proposed:** raising the timeout alone (7200 s already barely covers the measured
need and leaves a ~2 h stage as "normal"), pre-concatenating the 5 clips by hand
(out-of-system hand-finishing), or re-rendering any shots (all inputs are good).
